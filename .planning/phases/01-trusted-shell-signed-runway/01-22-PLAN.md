**Re-planned 2026-11-10 after 01-21's halt.** 01-21 is superseded by 01-24, which opted agent sessions out of the subprocess scrub (owner decision) and proved auto mode live. 01-25 added doctor's `Sandbox isolation settings` check and 01-26 the ninth probe row, `Credentials in the shell environment`, both through the CLI and the Trust API only. 01-24 runs agent sessions in auto mode. On claude 2.1.321 the halted 01-18 and 01-21 runs showed that claude can silently override the mode Counterpoint asks for. It printed `⚠ Permission mode forced to default …` on stderr and `permissionMode: "default"` in the init event. So `counterpoint doctor` must check the mode the probe's agent session really ran in, not the mode it was launched with. A future claude upgrade, or a settings source that turns the scrub back on, then cannot change the mode without failing doctor.

This plan records the effective mode from the treatment's init events, cross-checked with stderr, as an additive `agentMode` check in the `counterpoint/doctor/v1` report. Doctor fails anything but `auto`, the CLI prints it, and the Trust page shows it. The same Trust page change shows 01-25's isolation check, 01-17's eighth and 01-26's ninth probe rows and the updated all-pass wording, with the UI contract to match (Astryx only).

**Design notes:**
- *Where the mode comes from.*
  - Every `system/init` stream event carries `permissionMode`. The 01-18 and 01-21 evidence shows `"default"` with the forcing notice on stderr; 01-24's evidence shows what auto looks like (read its SUMMARY).
  - The treatment may run twice (a retry when a step was skipped), so every init event counts.
  - stderr is a cross-check: any line matching /permission mode|auto mode/i is a notice and fails the check, even if init said `auto` (fail closed).
- *Why a check row, not a probe row.* The mode is a property of the session, not a protected target. It renders like the other checks (`Pass`/`Fail`/`Not checked`) at the top of the Sandbox probe card, so probe rows keep their `Blocked`/`Reachable` words.
- *Schema stays v1.* `agentMode` is optional in zod, so older reports still parse. `reportVerdict` fails when it is missing or not `pass`, and the Trust page counts a missing one as not passing.
- *Single source for the expected mode.* `AGENT_PERMISSION_MODE` (src/agent/claude-argv.ts, cherry-picked from 01-21 by 01-24) is what the argv launches with, and doctor passes it as `expected`. Core (doctor-report.ts) receives it as a parameter, so core still imports nothing from `src/agent/`.
- *Two check rows, one card.* 01-25's `sandboxIsolation` check is the same kind of session-level check as `agentMode` (a `Check`, `Pass`/`Fail`/`Not checked`), so the Trust page lists both at the top of the Sandbox probe card, in the CLI's order: Agent permission mode, then Sandbox isolation settings. Its detail and fix words come from 01-25's `judgeSandboxIsolation` and are copied, never reworded.
- *Between Task 1 and Task 2.* Task 1 changes the server verdict, so the e2e fixtures that expect `Agents are boxed in` only pass again after Task 2 adds `agentMode` to them. Task 1 verifies with the unit project, and Task 2 runs both projects.
