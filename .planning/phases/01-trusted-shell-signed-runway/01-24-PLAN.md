  - env-vars.md "What the subprocess environment scrub removes": it strips credentials from the environments of the subprocesses Claude Code starts (Bash commands, hooks, stdio MCP servers), recognising a credential "by its variable name or by the shape of its value"; it leaves GitHub tokens and proxy settings in place. - *Precedence (settings.md).* `--settings` outranks user, project and local settings and is outranked by managed settings. So the explicit `autoAllowBashIfSandboxed: false` in the launch flag beats any user value; only a managed value could override it. 01-25's doctor check covers managed sources.
- *Auto mode's decision order (permission-modes docs, as recorded in 01-21's design notes).* Allow, ask and deny rules resolve first, and deny rules block in every mode. Read-only actions and file edits inside the working directory are approved without the classifier. Everything else goes to the classifier. Broad allow rules that grant arbitrary code execution (`Bash(*)` and its equivalents) are dropped on entering auto mode; narrow rules stay. So the treatment's bare `Bash` entry (AGENT_TOOLS) may have no effect in auto mode, and its non-denied Bash steps (the control-canary `cat`, the Keychain lookup) are decided by read-only approval or by the classifier.
- *The block (01-21 evidence, default mode).* The outside Write and Edit were refused with `permission_decision` `{decision: reject, source: config, reason_type: other}`, a `system/permission_denied` event with `decision_reason_type` `other` and `decision_reason` `Writes outside the working directories are blocked (permissions.blockWritesOutsideWorkingDirectories). Add the directory with /add-dir, or remove that setting.`, listed in `result.permission_denials`, and the text form `<path> is outside <dirs>; the permissions.blockWritesOutsideWorkingDirectories setting blocks writes outside the working directories. Ask the user to add the directory with /add-dir, or to remove that setting.` The git-hooks/git-info Write steps were refused by the deny rule (`reason_type` `rule`, `File is in a directory that is denied by your permission settings.`), not by the block. The docs name a second block text form, `<path>: Writes outside the working directories are blocked (permissions.blockWritesOutsideWorkingDirectories). …`.
- *The control attribution rule (owner guidance, 2026-11-10; 01-21).* The control is a measurement device: it proves each mirror twin is reachable and guarantees nothing. A control Bash step must be accepted with `reason_type` `rule`, covered by its own exact `Bash(<command>)` entry, with no exception. A control Read, Grep or Glob step whose planned path starts with `controlWorkdir` plus `/` and has no `..` segment counts as reached when accepted with `mode` (auto mode's read-only approval in the working directory). Every other control step must be accepted with `rule`. Any other accept fails. `controlWorkdir` is the recorded control request's cwd, kept only when every control init event reports that same cwd.
- *No observed decision source.* The stream names only the reason type of a permission decision, never the matched rule, and `permission_decision.source` read `config` on every 01-18 and 01-21 decision. The control's Bash attribution therefore rests on its launched allow surface (no bare `Bash`) plus the flagged user/managed-settings assumption.
- *Model.* The probe's `haiku` alias ran as `claude-haiku-5-5` in 01-18 and 01-21; the docs list Haiku 5.5 as supported for auto mode.
