<objective>
Fix the cause of WINDOWS.md #2 (owner decision: fix it in a Phase 1 gap plan before 01-16). Agent Write and Edit tools can write any user-writable file outside the session folder that no `Edit(...)` deny rule covers. The cause: the probe's treatment tool list, which is the production list, passes bare `Write` and `Edit` to `--allowedTools`, and under `--permission-mode dontAsk` a bare tool name is a grant over every path. `sandbox.filesystem.allowWrite: []` confines only Bash.

This plan makes the one production launch profile grant file edits only inside the session's working directory, through an `Edit(//{workdir}/**)` allow rule. Bare Write/Edit grants go away, and under dontAsk every other file edit is refused. It adds the eighth probe row, `Files outside the working folder`, to the planner, the evaluator, the report and `counterpoint doctor`, and proves it end to end with a fake claude.

This is slice 1 of 2 for WINDOWS.md #2. Slice 2 (01-18) runs the live probe, refreezes the fixtures, marks the window fixed and adds the row to the Trust page.

**Design notes (why this shape; read before Task 1):**
- *Why not an `Edit(//**)` deny with a workdir exception* (the other option WINDOWS.md #2 named). Claude Code evaluates deny, then ask, then allow. "An allow rule can't carve an exception out of a deny rule" (code.claude.com/docs/en/permissions). So that rule set would also block the workdir.
- *Why allow-only-workdir works.* The same doc says "`Edit` rules apply to all built-in tools that edit files". It also says dontAsk "auto-denies every call that would otherwise prompt", while `permissions.allow` rules still run. And file modification needs approval in every directory, the workdir included. The probe's control session already relies on this live on claude 2.1.319: its `permissions.allow` `Edit(//{mirror}/**)` let the Write tool create mirror files, and its `--allowedTools` never named Write (01-04).
- *No workdir, no edits.* When no workdir is given, the builder emits no allow side at all, so nothing can be edited (fail closed). `src/doctor/run.ts` builds a profile without a workdir only to look up target paths.
- *The expected denial for the new row is mode-family.* No deny rule covers an arbitrary home path, so the refusal comes from dontAsk ("…running in don't ask mode", `reason_type` mode). The existing seven rows keep their deny-rule evidence, because deny rules are evaluated first. The evaluator change is therefore scoped to the new row. It is justified by the probe's own knowledge of the launched treatment's allow side (`fileEditGrants`).
- *Considered, not adopted here:* `permissions.blockWritesOutsideWorkingDirectories` (Claude Code ≥ 2.1.314; installed: 2.1.321). It refuses Write/Edit/NotebookEdit outside the working directories in every permission mode. But its refusal is documented as a tool error, which may fire before our deny rules for the `.git/hooks` and `.git/info` Write steps. That would change the evidence of two existing rows. Adding it as a second layer is a separate owner decision (01-18-SUMMARY lists it as a recommendation).
- *Where the outside canary lives:* `{homeDir}/.cp-outside-{nonce}/`, the same class of location as `~/.claude/settings.json` and shell rc files. It is never under a deny rule and never inside the probe's working folder.
- *Read before Edit:* Claude Code's Edit tool refuses a file the session has not read, and does so before any permission check. So the row reads the canary first, as a preparatory step that never counts as a reach. Edit uses different old/new strings (RESEARCH Pitfall 1).
- *Schema stays v1.* The new target is an additive row. A report written before this plan has no such row, and `reportVerdict` fails it; Task 1 pins this with a unit test. Once 01-18 lists the row on the Trust page, the page renders it Not checked (existing `probeRows` behaviour, pinned by an 01-18 e2e case). The classifier change is recorded in the report's `matcherVersion` string (`{MATCHER_CLAUDE_VERSION}+r{MATCHER_REVISION}`), so the shape of the schema does not change.
