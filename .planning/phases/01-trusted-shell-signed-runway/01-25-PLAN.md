**Design notes:**
- *Literal "any source", narrowed only where a source cannot win.* `filesystem.disabled` and `excludedCommands` fail in every source, because user, managed and flag values all take effect (a scalar the flag leaves unset, a list that merges). The four Booleans the launch flag sets explicitly fail only in a managed source, because only managed settings outrank `--settings`; a user value for them cannot take effect, and failing on it would be a false alarm about a setting that changes nothing for agent sessions. Every present managed source is checked, whatever Claude Code's first-wins choice among them: that is stricter, never looser. The owner confirmed this effect-based reading of replacement 2 on 2026-11-10, after the plan check: `filesystem.disabled` and `excludedCommands` fail in every source; `enabled`, `failIfUnavailable`, `allowUnsandboxedCommands` and `autoAllowBashIfSandboxed` fail only in managed sources, because the launch flag outranks user settings.
- *Following links is deliberate.* The repo's safe-read pattern (01-PATTERNS: `O_NOFOLLOW`) protects Counterpoint's own state from planted links. Here the reader must see exactly what Claude Code sees, and Claude Code follows links (managed-settings docs; the owner's dotfiles may link `~/.claude/settings.json`). So the reader follows links, then requires a regular file. It is read-only and never writes.
- *Why a check row, not a probe row.* The setting is a property of the configuration, not a protected target; it renders like the other checks (`Pass`/`Fail`/`Not checked`) at the top of the Sandbox probe group, as 01-22's agent permission mode check will.
- *The probe path fails too ("doctor/probe fail", 2026-11-10 revision).* The check alone already makes doctor fail. The probe rows must not keep reading Blocked beside it, because a Blocked row is evidence of confinement only while isolation holds. The measured rows cannot be the enforcement on their own: with isolation off a step can still read Blocked when a deny rule refuses it, and keys such as `excludedCommands` or a managed `allowUnsandboxedCommands` leave the probe's own commands untouched. So `runDoctor`, after the probe, stores every measured Blocked row as Not checked while the check does not pass. This is the same post-probe rewrite it already does for the signing-key row when no key is trusted. Reachable rows stay as measured, because they are real exposure. `runSandboxProbe` gains no settings judgement: it measures, and each caller judges the settings its sessions launched under (doctor here; 01-23's live proof judges the launched `--settings` in `isolation.json`; 01-24's and 01-26's live tests assert the launched sandbox facts). Only doctor reads the user and managed files, because executors never read the owner's settings.
- *Between Task 1 and Task 2.* Task 1 makes a report without `sandboxIsolation` fail, so the e2e fixtures that expect `Agents are boxed in` stay red until Task 2 adds the field to them. Task 1 verifies with the unit project; Task 2 runs both.
