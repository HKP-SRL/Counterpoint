**Design notes (grounded in the installed binary and the docs, read 2026-11-10):**
- *Installed claude.* `claude --version` printed `2.1.321 (Claude Code)`. `claude --help` lists `--permission-mode` choices `acceptEdits, auto, bypassPermissions, manual, dontAsk, plan`. For `--permission-prompts none` it says: "nobody: anything that would prompt is denied automatically; the permission mode still decides everything else".
- *Auto mode's decision order* (code.claude.com/docs/en/permission-modes, "How auto mode evaluates actions"):
  1. Allow, ask and deny rules resolve first. Deny rules block in every mode. One exception that matters here: writes to protected paths (`.git`, `.claude`, shell rc files, …) go to the classifier even when an allow rule matches.
  2. Read-only actions and file edits inside the working directory are approved without the classifier.
  3. Everything else goes to the classifier.

  So an explicit allow rule decides before the classifier. That is why every control step gets one. The mirror's git layout is `{mirror}/git/...`, not `.git`, so it is not a protected path.
- *Broad allow rules are dropped.* On entering auto mode, blanket allow rules that grant arbitrary code execution (`Bash(*)` and its equivalents) are dropped; narrow rules such as `Bash(npm test)` stay. A bare `Bash` entry may therefore have no effect, and exact-command rules are what cover the control's Bash steps.
- *Which rule accepted a step is not in the stream.* In the 01-18 evidence every `tool_result_meta.permission_decision` holds only `{decision, source, reason_type}`, with no field naming the matched rule. With a bare `Bash` entry on the control, a `reason_type` `rule` accept of a control Bash step could come from that entry or from the exact-command rule, and the evidence could not tell them apart. So the control carries no bare `Bash` entry at all. The live run records the control's allow surface as launched, and a `rule` accept can then only come from the narrow entries recorded there.
- *No observed decision source either.* The `source` field read `config` on all 48 01-18 decisions (both sessions), and the init event has no field naming the loaded settings sources or rules. So the stream cannot say which settings source decided a step. The live run records the distinct control `source` values (`controlDecisionSources`). If one names a settings source, the SUMMARY records it per control step. Otherwise the SUMMARY says plainly that the attribution comes from the launched allow surface, not from an observed decision source.
- *The control attribution rule (owner guidance, 2026-11-10 guided revision).* The control is a measurement device: it proves each mirror twin is reachable and guarantees nothing. So, for every control step:
  - A Bash step must be accepted with `reason_type` `rule`, and its covering entry must be its own exact `Bash(<command>)` rule. This is the concern the bare-`Bash` removal addresses, and it has no exception.
  - A Read, Grep or Glob step whose path is inside the control's working directory counts as reached when accepted with `mode`, because auto mode approves read-only actions in the working directory without a rule. This covers the 01-18 shape below. "Inside" means the step's planned path starts with `controlWorkdir` plus `/` and has no `..` segment. `controlWorkdir` is the cwd of the recorded control request, kept only when every control init event reports that same cwd (probe.ts realpaths the probe dir, so in 01-18 the two strings matched).
  - Every other control step must be accepted with `rule`.
  - Any other accept fails the gate: a `mode` accept of a Bash, Write or Edit step (even inside the working directory) or of a path outside it, and any other reason type.

  The treatment is untouched by this rule: only deterministic refusals count there, and a classifier, mode or asyncAgent refusal never counts as Blocked.
- *Bash stays available unnamed (expected; checked live).* In 01-18 the control's Read, Write and Edit tools reached the mirror although `--allowedTools` named only `Bash` and the mirror Grep. Only Grep and Glob are removed when unnamed (01-04: `No such tool available: Grep`). The live run records every init event's `tools` list and fails on any `No such tool available`. If Bash turns out to be removed, stop rule (d) allows one fix: name the control's exact `Bash(<command>)` entries in `controlTools` too, never a bare `Bash`.
- *User and managed settings.* Besides the launch's own `--settings`, two settings sources can add allow rules to both sessions:
  - the owner's user settings, loaded through `--setting-sources user`;
  - managed settings, which load whatever `--setting-sources` says.

  At planning time the user settings held no `permissions.allow` entries, and neither file-based managed-settings location existed: `/Library/Application Support/ClaudeCode/` and `/Library/Managed Preferences/` (read-only checks, 2026-11-10). Server-delivered managed settings were not checked. Executors never read the owner's settings, so both are a flagged assumption, not a live check (see Flagged Assumptions).
- *The write block* (settings-reference `permissions.blockWritesOutsideWorkingDirectories`, claude ≥ 2.1.314):
  - It makes Write, Edit and NotebookEdit refuse paths outside the working directories in every permission mode, and "No allow rule lets Claude's file tools through".
  - It does not limit shell commands; Seatbelt (`allowWrite: []`) does that.
  - It also refuses writes to Claude Code settings files inside the working directories.
  - Claude-managed exempt files stay writable (plan files, the scratchpad, a background session's tmp, auto-memory `.md`). That is the existing T-01-70 residual.
  - It removes the `EnterWorktree`/`ExitWorktree` tools. Phase 2 builders run inside Counterpoint-made worktrees and do not need them.
  - Its documented refusal texts (errors.md): `<path> is outside <dirs>; the permissions.blockWritesOutsideWorkingDirectories setting blocks writes outside the working directories. …` and `<path>: Writes outside the working directories are blocked (permissions.blockWritesOutsideWorkingDirectories). …`.
- *The scrub.* env-vars.md documents `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` as stripping credentials from subprocess environments. The sandbox docs add that it keeps filesystem isolation on even when any settings source sets `sandbox.filesystem.disabled`, and that it turns the sandbox's auto-allow off. The docs say nothing about forcing a permission mode. The 2.1.321 notice `⚠ Permission mode forced to default — CLAUDE_CODE_SUBPROCESS_ENV_SCRUB is set (allowed_non_write_users hardening)…` is therefore a live-only fact, and step 4 decides it.
- *Model.* The docs list Haiku 5.5 as supported for auto mode. The probe's `haiku` alias ran as `claude-haiku-5-5` in 01-18.
- *The 01-18 shapes this plan must classify.* The outside Write/Edit were refused with `tool_result_meta.permission_decision` `{decision: reject, source: config, reason_type: asyncAgent}`, a `system/permission_denied` event with `decision_reason_type` asyncAgent and `decision_reason` `no approval surface in this session; permission request denied automatically`, and the message `Permission for this tool use was denied. It requires approval, and this session has no approval surface …`. Every other 01-18 treatment denial was `reason_type` `rule` or `subcommandResults`. Of the 24 control accepts, 22 were `reason_type` `rule`, all 9 Bash steps among them. The other two were `mode`. Both were Reads of paths directly in the control's working directory (the probe dir): the control canary and the control symlink. 01-18's control had no Read rule for either path. This plan adds one for each, so in auto mode they may come back as `rule` or still as `mode`, and the attribution rule above accepts either.
